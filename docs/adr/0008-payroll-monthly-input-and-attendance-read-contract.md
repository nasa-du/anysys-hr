# Payroll monthly input and attendance read contract

Payroll needs a monthly input value per employee before it can calculate: allowances, bonuses, administrative deductions, social insurance, tax, and advances. A second set of monthly values — full and attended days, paid leave, overtime hours, and the attendance deduction — already exists in the attendance module. The legacy requirement carried both sets in one monthly-import file, but the attendance effort established that attendance results are authoritative for payroll, that payroll reads them read-only, and that neither module writes the other's tables. The payroll domain model (ADR-0006) freezes configuration and a per-result attendance source snapshot at calculation time, but it does not say where pre-calculation inputs live, how a re-import replaces them, or how an attendance unlock after a payroll run is detected without attendance writing payroll tables.

We chose **one unified company + month payroll input, a file that carries only payroll-owned columns, and attendance values read only from a locked attendance month**. Payroll-owned values are stored as current state per payroll month and employee, with per-field provenance (`import` or `manual`); file imports are additionally kept as preview/commit batches with their parsed rows for audit. A successful commit replaces, for each importable column present in the file, that field for every employee in the payroll scope: employees present in the file get the file value, in-scope employees missing from the file get zero, and columns absent from the file are untouched. Manual edits write the same current-state values and are replaced by a later import of that column; the preview lists the manual values that will be overwritten. Attendance-owned values (the nine month-summary fields used by payroll) are never file-carried and never manually editable; they are read at calculation time from the locked attendance month's summary rows, and the calculation run records the attendance month, calculation run, locked snapshot, and calculation/rules versions alongside each result's nine values.

We chose this over batch-owned input rows (which would force manual edits to masquerade as an import batch and make the current values for a month hard to read), over letting the file carry attendance columns (which would duplicate the authority the attendance module already has and make conflicts a routine case), and over reading an unlocked or missing attendance month with a warning (which would calculate pay on provisional data; a missing summary also yields zero full-attendance days and either fails the default formulas with a zero denominator or silently underpays). We chose explicit calculation after a commit over automatic recalculation because a commit can succeed while the attendance month is still open, and because the attendance pipeline already established that imports never trigger calculation themselves. We chose to derive attendance staleness by comparing the last successful run's recorded snapshot and calculation-run identifiers with the current locked snapshot, rather than storing a stale flag written by attendance: attendance must not write payroll tables, and calculation always re-reads attendance, so a derived status is sufficient for reads and for the confirmation gate. We chose no revoke for committed batches; correcting a wrong file means importing the correct one, which leaves a clean audit trail.

## Consequences

- Payroll adds current-state input tables (`payroll_month_input`, `payroll_input_value`) and import audit tables (`payroll_import_batch`, `payroll_import_batch_row`); `payroll_month.input_version` increments on every successful commit or manual write, and each calculation run snapshots it.
- A payroll month can be imported and reviewed before the attendance month is closed, but it cannot be calculated until attendance is locked and every in-scope employee has a month summary.
- Re-import is a full-scope, per-present-column overwrite; the preview must show employees that will be zeroed or removed and manual values that will be replaced.
- Attendance staleness (`attendance_source_status`) and input staleness are derived at read/calculation time and are not stored columns. An attendance unlock after a payroll month is calculated or paid never rewrites results; it only makes the month stale, and paid months remain paid.
- A confirmed payroll month requires a fresh attendance source and unchanged input version; the payroll-month state machine (ADR to be recorded by the payroll lifecycle effort) adopts this gate.
- Committed and superseded batch metadata and normalized rows are retained for financial audit; preview batches expire after 24 hours; original file bytes are never retained; manual edits keep only the last writer.
- The attendance module stays the sole authority for attendance values, and payroll stays read-only against it; the two modules share no foreign keys.
