# Payroll configuration snapshots and explicit refresh

> **Partially superseded by [ADR-0009](0009-payroll-month-lifecycle.md).** Payroll recalculation no longer defaults to the stored configuration snapshot: a current payroll month resolves the latest configuration, while a historical payroll month reuses the last successful run's snapshot. The snapshot remains the audit and paid-reproduction record.

Payroll calculations depend on configuration that changes over time: compensation composition amounts, calculation-scheme formulas, workday parameters, global statutory parameters, field definitions, and position assemblies. The requirement asks compensation compositions to be versioned — a change creates a new version and old versions are retained — while the rest of the configuration has no explicit versioning requirement. Payroll months also need reproducible results after configuration edits, because a later formula, parameter, or assembly change must not silently rewrite a month that was already calculated, confirmed, or paid.

We chose **calculate-time configuration snapshots with explicit refresh**, combined with **identity plus immutable versions for compensation compositions** and **in-place edits with append-only revision snapshots for every other payroll configuration** (calculation schemes, workday parameters, global parameters, field definitions, and position assemblies). At calculation start the service resolves the current configuration for every employee — position → current composition version, calculation scheme and effective formulas, workday parameters, global statutory parameters, field definitions — and freezes it into the calculation run's `config_snapshot`. Results reference that run. Historical months continue to use their stored snapshot by default; configuration edits never rewrite existing results. Recalculating a month from its snapshot is the default; using the latest configuration requires an explicit “refresh to latest configuration” action. No effective-date auto-resolution is introduced in this phase: a version's effective dates are informational, and the snapshot is the historical truth. Positions reference a compensation-composition identity, not a composition version, so a newly created composition version automatically becomes current for future calculations while historical snapshots keep the amounts that were actually used.

We chose this over effective-dated configuration versions resolved by payroll month because the snapshot already makes every calculated result reproducible and the map's contract is snapshot plus explicit refresh; effective-dating would add overlapping-version, gap, and retroactive-change rules that the product does not need yet. We chose identity plus immutable versions for compositions because the requirement explicitly demands it and it gives positions a stable reference that survives amount changes. We chose in-place edits plus revisions for other configuration because full version tables for every entity would add UI and resolution complexity without improving result reproducibility beyond the snapshot. We rejected copying the full configuration into every result because the calculation run already groups employees sharing the same resolved configuration; a run-level snapshot avoids duplicating global parameters and formulas for every employee. We rejected recalculating historical months from live configuration because a later edit would silently change settled or previously calculated months, and we rejected storing no snapshot at all for the same reason.

## Consequences

- A payroll calculation run freezes `config_snapshot`; each result freezes its attendance source values and identifiers plus its attribution snapshot (department, position, and cost-center codes and names). Reprints and exports of a calculated month do not depend on live configuration or live organization data.
- Configuration edits mark affected months as needing recalculation but do not change existing results until a recalculation runs. Refreshing to the latest configuration is an explicit, audited action.
- Compensation compositions have immutable version rows plus one identity row that positions reference; the current version is the highest version number. Other payroll configuration entities have append-only revision snapshots with a monotonically increasing version number.
- The payroll module does not create cross-module foreign keys to attendance; attendance month and calculation-run identifiers are stored as values together with the attendance summary values used.
- Results store department, position, and cost-center identifiers without foreign keys, so payroll history never blocks deleting an unreferenced organization entity and is never rewritten when an employee transfers or an entity is deleted.
- The snapshot and revision rows add storage proportional to payroll months and configuration edits; that cost is accepted in exchange for reproducible results and a clear audit trail.
