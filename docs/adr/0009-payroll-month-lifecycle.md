# Payroll month lifecycle, overwritten results, and historical configuration

Payroll needs a month-level lifecycle from an editable draft to a settled payment, a recalculation contract that stays auditable when result rows are overwritten, and an explicit rule for which configuration a recalculation uses. The payroll domain model chose a configuration snapshot per calculation run and made the stored snapshot the default for recalculation, with an explicit refresh to adopt newer configuration. The monthly-input contract established that imports never trigger calculation and that attendance must be locked; the formula semantics made consistency failures atomic and deferred negative net pay to this effort. The requirement asks for draft/calculated/paid states, automatic marking of affected months after imports or configuration changes, one-click recalculation, and traceability of calculation time and data batch.

We chose a four-state payroll month (draft, calculated, confirmed, paid) with explicit confirmation and payment gates. Confirming or paying requires the month's most recent calculation run to be successful, the input version to be unchanged since that run, the attendance source to be fresh, and the employee scope to be unchanged; configuration staleness is advisory. A paid month locks results and inputs; unlocking requires a reason and returns the month to confirmed, retaining the paid snapshot. Confirmed months must be unconfirmed before recalculation. Paid months never recalculate. All logged-in users may perform every action in this phase, with the operator recorded.

Results are stored as **one current row per employee per payroll month**, overwritten by each successful calculation run; a failed run writes no results and leaves the previous results intact. Every attempt creates a calculation run with its trigger, status, configuration snapshot, input snapshot, attendance source, aggregate summary, error, operator, and timestamps. Inactive fields keep their last values together with the run that produced them, and employees who leave the scope are removed when a calculation succeeds. The run's snapshots and aggregate summary are the audit record for overwritten results; the paid snapshot is the only value-level historical record.

Recalculation resolves configuration by month class. A **current payroll month** — the current or a future calendar month that has never been paid — resolves the latest configuration. A **historical payroll month** — a month before the current calendar month, or any month that has ever been paid — copies the configuration snapshot of its most recent successful run; a historical month with no successful run falls back to the latest configuration because no snapshot exists. Historical months have no explicit "use latest configuration" override in this phase, and effective-dated configuration resolution remains out of scope. This supersedes ADR-0006's rule that recalculation defaults to the stored snapshot and that adopting newer configuration requires an explicit refresh.

Each payment appends a self-contained payroll month snapshot containing the paid results, configuration snapshot, input snapshot, attendance source, attribution snapshots, and payslip presentation data (labels, categories, order, visibility, and totals at payment time). Unlocking retains the snapshot; paying again appends a new version. An append-only payroll month event records confirmation, unconfirmation, payment, and unlocking with the operator, reason, and calculation run.

Input, attendance, and scope staleness are derived at read time; configuration staleness is stored per month and recorded only for current months, because historical months intentionally keep their snapshot. Needs-recalculation is derived from those sources, and configuration staleness never blocks confirmation or payment; attendance and scope staleness do. Attendance failures, configuration failures, formula runtime errors, consistency failures, and an empty scope fail the whole run atomically; negative net pay and ignored out-of-scope inputs are warnings.

Only an empty draft month — a draft with no successful run, no paid snapshot, and no committed import batch — may be deleted. Calculated, confirmed, and paid months, their runs, results, and paid snapshots are never deleted or archived in this phase. Corrections after payment happen through unlock, unconfirm, recalculation, confirm, and pay again; automatic red reversal, supplemental payment, and cross-month retroactive adjustment are out of scope.

## Consequences

- Pre-payment recalculation history keeps run metadata, snapshots, and aggregate totals but not per-employee result values; the paid snapshot is the only retained value-level history.
- Recalculating a historical month cannot adopt configuration changes made after its last successful run; correcting a configuration error in a settled month needs a future correction effort.
- Recalculating a current month adopts the latest configuration, so formula, parameter, and composition changes can change current-month results.
- Result queries are simple, and each result value records the run that produced it even when the row is overwritten.
- ADR-0006's snapshot-default recalculation rule is superseded; its configuration snapshot remains the audit and paid-reproduction record.
- The first calculation of a historical month with no prior successful run uses the latest configuration; without effective dating there is no way to reconstruct an older configuration for that first run.
