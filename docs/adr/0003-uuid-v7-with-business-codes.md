# UUID v7 primary keys with separate business codes

Every organization and employee entity keeps a UUID v7 `id` as its primary key and carries a separate, immutable business code — `company_code`, `dept_code`, `position_code`, `cost_org_code`, or `employee_no`. The requirement uses human-readable codes as the external key for Excel imports and cross-system matching (company `C1`, department `D1`, employee number), while [ADR-0001](./0001-uuid-v7-primary-keys.md) requires time-ordered UUID v7 primary keys for new entities. All foreign keys reference the UUID; business codes are unique identifiers for imports, human reference, and integration, and are never used as foreign keys. `company_code` and `employee_no` are globally unique; department, position, and cost-center codes are unique within a company.

We chose two identifiers over using the business code as the primary key because codes are entered by users, can contain mistakes, and have different uniqueness scopes per entity; a code-as-key design would make correcting a code a cascading foreign-key operation and would tie referential integrity to an external naming convention. Using only UUIDs was rejected because the requirement's import flow matches rows by code and users need a stable, readable identifier; exposing UUIDs in Excel templates would be worse. The cost is a second identifier to maintain, plus immutability and uniqueness rules; the benefit is that internal identity and external naming can evolve independently. Codes are normalized to uppercase, validated against `^[A-Z0-9_-]{1,32}$`, and immutable after creation. UUIDs remain the only foreign-key targets; APIs may expose both, and the UI displays codes.
