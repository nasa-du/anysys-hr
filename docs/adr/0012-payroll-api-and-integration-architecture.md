# Payroll API and integration architecture

Payroll is the second large module after attendance: 81 endpoints across six configuration resources, monthly input/import, the payroll month lifecycle, results, payslips, reports, cost statistics, and asynchronous exports. It must reuse the repository's FastAPI + SQLModel + PostgreSQL conventions, keep company context explicit, and stay implementable without introducing a queue or a service mesh. This ADR fixes the API surface, the attendance integration path, the migration strategy, and the export worker shape before the implementation-order ticket and the payroll specification can be written.

We chose a **resource-oriented REST API under `/api/v1/payroll`** with fifteen OpenAPI tags that map one-to-one to generated frontend services. Collections return `{data, count}` with `skip`/`limit`; the payroll list additionally returns `fields` (current field definitions or the paid snapshot's frozen field metadata) and `totals` over the filtered set. Configuration writes are aggregate saves guarded by `base_revision_no` (or `base_version_no` for immutable composition versions), returning 409 `config_revision_conflict` / `composition_version_conflict` instead of silently overwriting another user's edit. Calculation is synchronous with a 60-second wall-clock deadline, matching attendance; a separate read-only checklist endpoint exposes the preflight gates so opening a month does not aggregate attendance and scope on every read. All exports write a `payroll_export` audit row; single payslip PDFs, payroll-detail Excel, and department-summary Excel are synchronous downloads, while batch ZIP and merged PDF are asynchronous jobs.

We chose to **read attendance through an in-process, read-only contract**, not internal HTTP. A narrow function in the attendance service loads the locked attendance month, its locked snapshot, and the month-summary values into frozen dataclasses; payroll maps missing/unlocked/missing-summary/inconsistent cases to its own blockers. Attendance never imports payroll, payroll never writes attendance, and calculation can run in one database session and be tested with a fake reader. The direction of the dependency is part of the decision.

We chose **four DDL migrations after the attendance head and a startup seed for system defaults**. The migrations are `payroll_config` (nine tables), `payroll_months` (six), `payroll_inputs` (five), and `payroll_exports` (one). The thirty-two system field definitions and six global parameters are not sample data: they are system configuration required before any company can calculate. They are inserted idempotently from `app/initial_data.py` with `ON CONFLICT DO NOTHING`, keeping migrations row-free and the existing migration test intact; the same function runs in tests.

We chose **one export worker service and a shared named volume**. The worker is the same image with a different command, polls `payroll_export` with `FOR UPDATE SKIP LOCKED`, renders WeasyPrint/OpenPyXL output with four processes, and writes artifacts to `payroll-exports:/app/exports`; the backend mounts the same volume read-only and streams downloads after authentication. There is no Redis, Celery, or multi-instance coordination in this phase. The worker marks stale running jobs failed on startup and enforces the 24-hour artifact TTL.

We chose **in-memory pivoting for the payroll list and reports**. Header filters and the result row set are selected in SQL; one query loads the values for the filtered set, and the service pivots, sorts, totals, and pages in Python. With the agreed 1,000-employee target and at most a few dozen fields, this is simpler than dynamic SQL crosstabs, keeps custom fields first-class, and meets the two-second p95 target. The same approach drives cost statistics and department summaries.

Alternatives rejected: `page`/`page_size` pagination (inconsistent with attendance and the ticket's `skip`/`limit` instruction), internal HTTP between payroll and attendance (extra transaction and auth boundary, harder testing), asynchronous calculation jobs (unnecessary inside a 60-second deadline), composite foreign keys for same-company integrity (the repository validates cross-company references in services; composite keys add columns and migrations for a rule the service already owns), a data migration for default fields (breaks the migration zero-row contract and makes downgrade ambiguous), a per-export-type endpoint family for every sync/async combination (200/202 unions generate poor clients), duplicating the attendance file parser (two security surfaces), SQL crosstabs for dynamic result columns (custom fields make them dynamic and fragile), and multi-instance workers or Redis/Celery (operational cost with no scale need).

## Consequences

- The API shape, tag names, pagination, error envelope extensions, and generated client are fixed for the implementation slices; changes after this point are breaking API changes.
- Payroll and attendance are coupled in one direction only: payroll imports the attendance read contract; attendance code must not import payroll.
- Calculation is synchronous and bounded; failed runs are retained with their snapshots, and the month state and current results are unchanged on failure.
- Configuration edits are optimistic and audited; concurrent editors receive a conflict instead of overwriting. Revision records are permanent.
- The export worker is a deployment dependency and must be included in compose and CI; the shared volume is part of the runtime contract.
- Four new migrations and a startup seed are required; tests must add a payroll table registry, update the "no payroll tables" assertion, and seed defaults in conftest.
- The payroll list/report query strategy is intentionally in-memory for the 1,000-employee target; larger scales would need a different plan.
